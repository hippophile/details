# Change: llm-streaming

## Driver
User, 2026-11-04: "do them all". Feature D of `design/v2/SPEC-RULES-v2.1.md`: "Analysis output text appears token by token while Gemma writes (LM Studio streaming). Validation still happens at the end."

## Depends on
- Implemented: `llm-outputs` (analysis-outputs): `llm/client.py`, `llm/pipeline.py`, `runner/steps_analyse.py`, the Analyse page outputs.
- **`run-insights` must be applied first** (order 1 -> 2): this change edits the `chat` wrapper in `steps_analyse.py` that run-insights introduces (call log line, step metrics) and adds `stream` fields to that log line. `live-assistant` (later) may reuse `client.chat_stream` and the hub; it does not have to.

## Spike result (measured 2026-11-04, running LM Studio, already-loaded `google/gemma-4-e4b`, 2 tiny read-only requests, no load/unload)
- `POST /v1/chat/completions` with `stream:true` **and** `response_format` `json_schema` (strict) **does stream** : OpenAI-style SSE `data: {...chunk...}` lines; the first chunk has `delta.role` + first `content` piece, then one `delta.content` per token-ish piece, an empty-content chunk, a chunk with `finish_reason:"stop"`, then (with `stream_options:{include_usage:true}`) a final chunk with `choices:[]` and `usage:{prompt_tokens, completion_tokens, ...}`, then `data: [DONE]`. With `reasoning_effort:"none"` no reasoning deltas appeared.
- **Not yet proven** (task 1 spike): (a) closing the HTTP connection mid-reply makes LM Studio stop generating (tok/s drops to idle), (b) `finish_reason:"length"` arrives on a cut-off long reply, (c) behaviour of the 26B model and of a model that rejects `stream_options`, (d) a mid-stream server error shape. The design below does not depend on (c)/(d): it falls back.

Not touched: `quotes.py`, `schemas.py`, migrations (none), `analysis_run` columns.

## Decision
0. **Cross-change contracts (binding).** Hub/stream routes live in `api/jobs.py`; `add_jobs_routes(app)` reads settings/data_dir from app keys. Uses run-insights' `bind(pool, *, memory=None, settings=None, hub=None)` (the hub is passed through `hub=`). Hub events carry only what is knowable at the wrapper (attempt start/end, deltas, tokens); validity and chunk position come through the `on_event` callback that `pipeline.call_validated/generate_kind` now accept (`on_event("attempt_end", valid=..., ...)`, `on_event("chunk", i, n)`).
1. **Contract stays identical.** `client.chat_stream(settings, *, model, kind, schema, messages, max_tokens, on_delta, cancelled)` returns exactly the dict `chat` returns: `{text, tokens_in, tokens_out, finish_reason, wall_ms, raw}`. `text` = all `delta.content` concatenated (never `reasoning_content`). `raw` = `{"stream": true, "chunks": <count>, "usage": {...}, "finish_reason": ...}` (not every chunk; the chunk bodies add nothing the text does not already hold). validation, the one retry and the quote check therefore run **unchanged on the final text, after the stream ends**.
2. **Tokens.** Request adds `stream_options:{include_usage:true}`. `tokens_in/out` come from the usage chunk. If no usage chunk arrives, `tokens_out` = number of non-empty content deltas and `raw.usage_estimated=true` (estimate, not measured); `tokens_in` = 0 and logged as unknown.
3. **Setting.** `[llm] stream = true` (`DETAILS_LLM_STREAM`), `[llm] stream_idle_timeout_s = 60` (no bytes for this long = the call fails; replaces the whole-call timeout for streamed calls because a long reply is normal while a silent socket is not). `settings.py` + `config.toml` edited.
4. **Fallback to non-streaming.** One automatic fallback to `client.chat` (same request with `stream:false`) when the streaming request fails **before the first content delta**: HTTP 400/422 mentioning `stream`/`stream_options`, a non-SSE content type, a body with no parsable chunk, or `[DONE]` with no content. The call log line says `mode=plain, fallback=<reason>`. After the first delta there is **no** fallback (it would silently double the generation): a mid-stream drop is an `LLMError("stream ended early")` and goes through the existing failure path. If a fallback happens the run is remembered per model in memory for the rest of the job (no flapping).
5. **Stream hub (in memory, per job).** `StreamHub` keeps, for each running job, the text of the **current attempt only** (cap 256 KB; typical replies are a few KB) with a seq counter, and events `attempt_start{kind, attempt, chunk?}`, `delta{text}`, `attempt_end{valid?, finish_reason, tokens_out}`, `fallback{reason}`. The `chat` wrapper opens an attempt per call, so the existing retry and map-reduce chunks show up as new attempts with no pipeline change. The hub is not persisted: after a restart or when the job ends, the buffer is dropped; the final `analysis_run.raw_response` remains the record.
6. **SSE endpoint** `GET /api/jobs/{id}/stream`: first event = `snapshot` (current attempt text so far, so a late subscriber or reload sees the whole text), then `delta` events; the server coalesces output to at most one write per 100 ms; `id:` per event, `Last-Event-ID` resumes from the buffer else resends a snapshot; `: ping` every 15 s; the stream closes when the job is terminal. 404 unknown job; a job that is not streaming gets a `snapshot` with empty text and then only `status` pings until it ends. The existing `/events` is not changed.
7. **Cancel mid-stream.** `chat_stream` races each read against `ctx.cancelled`; when set it closes the response (so LM Studio stops generating, proven in the spike), raises a dedicated `StreamCancelled` that is NOT an `LLMError` (so the `except LLMError` branch at `steps_analyse.py:113-117` that writes `failed` is not taken; additionally that UPDATE is skipped when `ctx.cancelled.is_set()`), and nothing partial is stored: no `output` row, every `analysis_run` row ends `cancelled` via the finalizer and run-insights unloads the model. Expected latency: under 1 s, not the 5 s runner grace. The partial text is shown on the page until the job status arrives, then replaced by "Cancelled".
8. **Page.** While the `analyse` step runs, a "Gemma is writing" box in the Running card shows the raw JSON as it arrives (monospace, auto-scroll, `textContent` only), a header `debrief · attempt 1 · 320 tokens · 41 tok/s` computed client-side from delta count and time, a marker `retrying` when an attempt restarts after invalid JSON, and `chunk i/n` in map-reduce. When the kind finishes, the box is cleared and the validated result appears as today (no change to outputs UI). Raw JSON is shown on purpose: parsing partial JSON into pretty text would risk showing text the validator later rejects, which the user asked to avoid ("validation still happens at the end"). The box is labelled "draft, not yet checked".
9. **Logging (uses run-insights).** The LM call line gains `stream:true|false`, `ttft_ms` (time to first delta), `fallback`. Delta text is never logged.
10. **Out of scope:** pretty incremental rendering of partial JSON, streaming for the STT steps, persisting partial text of cancelled calls, a "stop and keep what I have" button, streaming in `live-assistant` (it may opt in later).

## Verification
- Red first: fake LM Studio streaming mode + tests fail before `chat_stream` exists.
- Client: chunked fixture -> same `text/tokens/finish_reason` as the non-stream fixture for the same content; usage-less stream -> estimated tokens flagged; `reasoning_content` deltas ignored.
- Fallback: server returns 400 for `stream` -> exactly one plain call, result identical, log says fallback; failure after the first delta -> `LLMError`, no second call (assert request count).
- Validation unchanged: invalid JSON streamed -> same retry, same `analysis_run` rows and `schema_valid=false` handling as today (reuse the llm-outputs scenarios with streaming on); an unverified quote is still flagged `verified:false`.
- Cancel: slow fake stream, cancel after 3 deltas -> fake sees the connection closed, job `cancelled` within 1 s, ALL `analysis_run` rows == `cancelled` (none `failed`), no `output` row, partial text not in the DB.
- SSE: late subscriber gets a snapshot with the text so far; two subscribers see the same text; closes at terminal; 404 unknown job.
- **Negative:** no delta text and no prompt in `log.jsonl`; a fake stream whose error chunk echoes `password=SeCr3tPw` leaves the secret out of log, hub snapshot, job error and `GET /api/analyses/{gid}` `.error` (`chat_stream` calls `redact()` on error text like `chat`).
- Real: `@pytest.mark.gpu` test with the loaded E4B streams a short checklist and the final output equals a non-streamed validation result structurally (not text-equal).
- Page: JS tests for the delta accumulator and tok/s header; Brave screenshot mid-stream of the live box.

## Caveats
- Streaming adds no speed; it only shows progress. tok/s shown live is client-side from chunk arrival (estimate, not measured by LM Studio); the stored value remains `tokens_out / wall_ms` from usage.
- Raw JSON in the box looks technical by design (see 8).
- After the first delta there is no fallback; a mid-stream failure fails the attempt (and then the usual single retry applies at the pipeline level for invalid output, not for transport errors, which is today's behaviour).
- The live view is per server process; if the page opens after the job ended it shows only the final result.
- A model that ignores `stream:true` and answers with one JSON body is handled by the fallback rule (non-SSE content type).

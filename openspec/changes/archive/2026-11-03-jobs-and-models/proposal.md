# jobs-and-models

## Driver
"One job at a time on the GPU, steps in sequence: speech, unload, speakers, unload, AI. This never swaps on 32 GB. Jobs survive closing the tab and restarting the server." and "Models are config: adding a model = one config block." (DESIGN.md §1, §5). LM Studio models are loaded/unloaded via `lms`; the app only unloads models it loaded itself.

## Depends on
`v2-foundation` (Settings, `create_app`, db, migrations, test DB fixture) and `recording-capture` (migration 0002: `job.recording_id` references `recording`). `library-page` is not required. Consumed later by `stt-runs` and `llm-outputs`, which plug steps in.

## Decision
1. **Registry** (`models.toml`, loader in `services/models.py`): tables `[stt.<id>]` (`engine` = `mlx_whisper`, `label`, `repo`, `needs_gb`, `langs`, `options`, `role`, `enabled`) and `[llm.<id>]` (`engine` = `lmstudio`, `label`, `model` = LM Studio model key, `context`, `needs_gb`, `role`). `engine` outside `mlx_whisper` (STT) / `lmstudio` (LLM) is a load-time error with a clear message naming the entry. `role` is one of `cheap|nice|fast|accurate`. Later changes add no duplicate entries. Shipped entries: STT `whisper-turbo`, `whisper-large` (engine `mlx_whisper`, repos `mlx-community/whisper-large-v3-turbo` / `whisper-large-v3-mlx`); LLM `gemma-cheap` (E4B) and `gemma-nice` (26B QAT) role `cheap`/`nice`. LM Studio base URL is `settings.lmstudio.url` (`DETAILS_LMSTUDIO_URL`) and the `lms` binary is `settings.lmstudio.cli`; neither lives in an entry. LM Studio model keys come from the task-1 spike (real `lms ls --json` `modelKey`): `gemma-cheap` = `google/gemma-4-e4b`, `gemma-nice` = `gemma-4-26b-a4b-it-qat-mlx`. Unknown engine/backend or missing field is a load error naming the entry.
2. **`GET /api/models`**: `{stt:[...], llm:[...], lmstudio:{reachable}}`; each entry `{id, kind, label, engine, role, needs_gb, installed, unavailable_reason?, hint?}`. `?kind=stt|llm` returns a flat list. Any POST that names an unknown model id (e.g. `lm_load` params, enqueue-time validation of `model_id`) returns 422. `installed`: STT = HF hub cache has weights for `repo` (same check as v1 `models()`, using `HF_HOME`); LLM = key present in controller `list_downloaded()`; LM Studio unreachable gives `installed:false` with `unavailable_reason`, plus `lmstudio.reachable:false`, not a 500.
3. **Job table** (0003): `job(id uuid pk default gen_random_uuid(), recording_id uuid null references recording(id) ON DELETE CASCADE, kind text, params jsonb, steps jsonb (ordered step names), status text check in queued|running|cancelling|cancelled|failed|done, step text, step_index int, step_progress real, message text, error text, attempt int default 0, created_at, started_at, finished_at, heartbeat_at)`. Index on `(status, created_at)`. Progress/heartbeat writes are throttled to one per second per job.
4. **Step interface** (`runner/steps.py`): `steps = StepRegistry()`; a step is `async def run(ctx: StepContext) -> dict | None` registered with the decorator `@steps.register("name")`. Step modules `runner/steps_stt.py` and `runner/steps_analyse.py` (owned by stt-runs and llm-outputs) are imported in `create_app`; this change creates neither. Finalizers: `@steps.on_terminal("name")` async functions `(job, status, error)` run when a job ends `cancelled` or `failed`, **including when it is cancelled while still queued** (then for every step of the job not yet done); finalizer errors are logged and do not change the job status. `JobService.enqueue(kind: str, recording_id: UUID|None, steps: list[str | {"name","params"}], params: dict = {}) -> job_id` (HTTP: `POST /api/jobs {kind, recording_id, steps, params}`; unknown step name -> 422). `StepContext` fields: `job_id`, `step_name`, `params` (step params merged over job params), `cancelled` (asyncio.Event), `step_dir` (the ONLY checkpoint dir, `<data_dir>/jobs/<job_id>/<step>/`), `data_dir`, `settings`, `memory` (MemoryManager), `progress(pct, msg)`, `spawn_child(argv)` (starts a subprocess, reads stdout lines as heartbeat, registered so cancel can kill it). Child protocol: one stdout line at model load and at least one per window. `stt-runs` and `llm-outputs` register real steps; here only fakes exist. **Built-in steps** (registered here): `lm_load` (params `model_id`) and `lm_unload`, thin wrappers over MemoryManager. STT steps call `await ctx.memory.release_for_stt()` before spawning.
5. **JobRunner** (`runner/runner.py`): one asyncio worker task, FIFO by `created_at`. Per step: take `GpuLease`, run, then write `done.json` atomically (`.tmp` + `os.replace`) in the step dir and only then advance `step_index`. On start: `running` and `cancelling` jobs become `queued`; steps with `done.json` are skipped. Retry: `POST /api/jobs/{id}/retry` on a `failed` job sets `queued`, keeps done steps, restarts at the failed step. Cancel: `POST /api/jobs/{id}/cancel` sets `cancelling`, SIGTERM the child, SIGKILL after 5 s (config), sets the cancel event, ends `cancelled`; partial files stay. Heartbeat: no heartbeat for `runner.heartbeat_timeout_s` (default 120, config) kills the child and fails the job with step name and "no heartbeat". No auto-retry.
6. **GpuLease** (`runner/lease.py`): asyncio lock with owners `job` and `live`. `live` is granted ahead of waiting jobs; a running step is never interrupted, the next step waits. API only here (`acquire(owner)`, `async with`); wiring Record page to it is `recording-capture`/later.
7. **Progress API**: `GET /api/jobs/{id}` returns the job JSON; `GET /api/jobs/{id}/events` is SSE with events `{"seq","job","status","step","pct","msg"}`, first event = current state, then changes; sends `id:` per event and closes after a terminal status. `POST /api/jobs` (`kind`, `recording_id`, `params`, `steps`) enqueues; `GET /api/jobs` lists recent. Events are derived from job state, no event log table.
8. **LM Studio controller** (`llm/lmstudio_ctl.py`): `list_downloaded()`, `list_loaded()`, `load(model_key, identifier, context)`, `unload(identifier)`. Transport chosen by the task-1 spike (`lms ... --json` subprocess vs REST `/api/v0`); the controller depends on a small `Transport` protocol so fakes and either choice fit. Loads always pass `--identifier details-<registry id>`.
9. **MemoryManager** (`runner/memory.py`): tracks identifiers it loaded (`details-` prefix, also persisted by reading `list_loaded()` so a restart still recognises them). `ensure_llm(entry)`: unload other app-loaded models, then load. `release_for_stt()`: unload app-loaded models. Never unloads a model whose identifier lacks the prefix (unless config `lmstudio.exclusive = true`, default false). Preflight: reads free+inactive memory through a `MemInfo` protocol; if `needs_gb` exceeds it, unload owned models and re-check, else fail the step with "needs ~X GB, Y GB free". Swap guard and measuring script are v2.1.

## Verification
- All behaviour tested with `FakeStep`, `FakeLMStudio` (records calls, returns recorded JSON), `FakeMemInfo`; no GPU, no LM Studio. A crash test starts a real subprocess child running a fake script and cancels it.
- Negative cases: failed step stops the job (no later steps run, no auto-retry); a model without the `details-` prefix is never unloaded; unreachable LM Studio gives `installed:false` not 500; no-heartbeat child is killed; invalid `models.toml` names the bad entry.
- One real contract check, marked `gpu` (run by hand): controller lists real models via the installed `lms`.
- Test children use short sleeps (<=5 s) and every test has a timeout (`pytest-timeout` marker or `asyncio.wait_for`), so a failing cancel test cannot hang the suite.
- Manual: curl `/api/models`, create a fake job, watch `curl -N .../events`, restart server mid-job and see it resume.

## Spike findings (2026-11-03, lms CLI commit 43d4b26, run for real)
- `lms ls --json` -> list of `{type, modelKey, displayName, path, sizeBytes, maxContextLength, ...}`; `lms ps --json` -> list of `{modelKey, identifier, contextLength, status, ...}`. One load/unload round trip of E4B with `--identifier details-spike -c 4096 -y` appeared in `ps` as a second instance beside the user's model (`identifier` = `details-spike`, `contextLength` 4096) and `lms unload details-spike` removed only it.
- REST `GET /api/v0/models` puts the *identifier* of loaded instances and the *model key* of downloaded models in the same `id` field, and has no load/unload. **Decision: CLI transport (`lms ... --json`); REST is used only as the reachability probe against `settings.lmstudio.url`.**
- Fixtures `tests/fixtures/{lms_ls,lms_ps,lms_ps_loaded,rest_models}.json` are real output (no STUB files).

## Implementation notes (corrections to the text above)
- `StepContext` has 10 fields (the task text said 9): `job_id, step_name, params, cancelled, step_dir, data_dir, settings, memory, progress, spawn_child`.
- `done.json` holds `{index, step, result}`; a marker is honoured only when its `index` equals the step's position, so a step name used twice in one job does not skip its second run.
- `ctx.progress(pct, msg)` takes a fraction 0..1 and may be called plainly or awaited. `ctx.spawn_child(argv, on_line=None)` is awaited, returns `ChildResult(returncode, lines)` and raises `StepError` on silence or non-zero exit.
- Purge also skips recordings whose job is `cancelling`.
- `create_app` gained injection args `step_registry`, `lm_transport`, `meminfo` (tests); settings gained `[lmstudio] exclusive`.
- Existing tests touched for this change: `test_migrate.py` (ignore 0003 when copying migrations), `test_recording_migration.py` (job table allowed), `test_settings.py` (CFG has the new keys), `test_library_purge.py` (job tests un-skipped).
- A hard-killed server (SIGKILL) leaves a running child orphaned (children run in their own session); a normal SIGTERM shutdown kills them.

## Caveats
- If the lms spike cannot run (LM Studio not available), tasks 2-9 proceed against stub fixtures hand-written from `lms --help`; the spike is then re-done before archive and fixtures corrected.
- `lms` JSON shape and REST fields are unverified until task 1; the LM Studio model keys in `models.toml` are placeholders until then. If `lms` behaves differently, only the transport changes.
- Resume granularity is per step in this change; per-window STT resume is `stt-runs`' job via the `step_dir`.
- Memory numbers in `needs_gb` are estimates, not measured.
- Live-vs-job priority is implemented in `GpuLease` only; the Record page does not take the lease yet.
- Single local user, no auth on `/api` (127.0.0.1 only).

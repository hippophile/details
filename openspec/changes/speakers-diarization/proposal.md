# Change: speakers-diarization

## Driver
User, 2026-11-08: "who talked" for meeting recordings. `design/v2/DESIGN.md` section 5: "**Who talked:** pyannote **community-1**, run offline after STT and aligned by time overlap. It needs a **free Hugging Face token once** (gated model)." Data model line: `recording -> stt_run -> (diarization_run) -> analysis_run`. The result is a Speakers view (talk time, turns, click-to-seek, rename) plus speaker-labelled transcript text for debrief and notes. Recordings are mostly Greek with some German, 2-3 people, 10 to 60+ minutes; the speaker count is unknown.

## Caveats (read first)
- **Speaker labels are a guess.** DESIGN.md cites about 17-20% diarization error on meeting corpora (AMI-IHM 17.0, AMI-SDM 19.9 DER on the model card, via `design/v2/ml-engineer.md`). Roughly 1 second in 5-6 is mislabelled; overlap and short interjections are worst. The tab says so and nothing here claims better.
- **Not proven on this user's audio.** One person reading three voices is one voice to a speaker model. The real quality check needs a 5 minute recording with a second real person; until then only fakes are tested in the default suite and the `gpu` test proves that the model runs and returns turns, not that they are right.
- **One-time Hugging Face step.** The model is gated: create a free HF account, accept the terms on the model page, create a read token, put `HF_TOKEN=...` in `.env`, run `make setup-diar` and `make diar-model`. Never paste or screenshot the token. Until then the UI shows diarization disabled with exactly these steps.
- **Heavy dependency, verified install (2026-11-08).** `pyannote.audio` 4.0.7 added 57 packages to `.venv` and changed none of torch 2.15.0, mlx, mlx-whisper, numpy, psycopg, aiohttp (dry run first, then install); it imports next to mlx-whisper. Pins are in `requirements-diar.txt`. The model itself is not downloaded yet (needs the user's token, task 9.2), so loading and running the real pipeline is still unproven.
- **pyannote 4.x reports usage metrics by default** (audio duration, speaker-count hints, version, session id to `otel.pyannote.ai`; no audio or text). The worker turns this off with `PYANNOTE_METRICS_ENABLED=0` (decision 6). Read from the source, network not captured.
- **CPU by default, MPS opt-in.** See decision 8. Speed on this Mac is an estimate ("minutes, not hours" for 2.5 h, `ml-engineer.md`), not measured.
- **RAM is conditional.** Peak is the pipeline plus decoded audio on top of whatever else is loaded. The app unloads only the LM Studio models it loaded (`details-*`); a model you loaded yourself stays, so with a 26B of your own loaded the headroom is smaller (`lmstudio.exclusive` changes that). Not measured.
- **Whole-segment labels.** Each transcript segment gets one speaker (largest overlap). A segment where two people spoke is given to the one who spoke longer, so talk-time % (from turns) and the labelled text can disagree; the card says so.
- **The GPU is shared.** While speakers are detected the lease is held, so Live assist on the Record page waits (it is not interrupted either way); the button has a line saying so.
- The cached model works offline without a token (decision 7); this is a deliberate reading of "token or model missing".

## Decision
1. **Separate steps, own tables, migration 0009.** New job kind `diarize` with one step `diarize` (module `runner/steps_diar.py`, added to `STEP_MODULES`). Tables `diarization_run`, `diar_turn`, `speaker_name`, plus `analysis_run.diarization_run_id` (nullable, `ON DELETE SET NULL`). Every FK to `recording` cascades. Runs are append-only; only `speaker_name` is mutable.
2. **Diarization belongs to the recording, alignment happens at read time.** `diarization_run.recording_id` (no `stt_run_id`). Turns are audio facts; the segment-to-speaker mapping is a pure function in `services/diarization.py` applied to whichever `stt_run` is on screen. Nothing is written into `transcript_segment`, so re-transcribing never forces a re-run and an alignment fix needs no migration. STT is not a prerequisite for the API (decision to challenge); the UI offers the button next to a transcript and the GPU lease keeps STT and diarization sequential.
3. **Engine = pyannote `speaker-diarization-community-1` as its own child process**: `python -m details.engines.diar_worker <spec.json>`, same pattern as `engines/worker.py` (spec file in, atomic result file out, stdout heartbeat, cancel = kill). The step calls `await ctx.memory.release_for_stt()` before `spawn_child`, so app-loaded LM Studio models are unloaded first. Uses `output.exclusive_speaker_diarization` (no overlapping turns, built for transcript alignment per the model card). Optional `min_speakers`/`max_speakers` hints (whole numbers 1-10, min <= max) are passed through; absent = engine decides.
4. **Registry: new `[diar.<id>]` block kind.** `models.toml` ships one entry `community-1` (`engine = "pyannote"`, `repo = "pyannote/speaker-diarization-community-1"`, `needs_gb = 3` estimate, not measured, `role = "accurate"`). `services/models.py` allows engine `pyannote` for `diar` only; `Registry.diar` defaults to `{}`; unknown engine stays a load-time error naming the entry. `GET /api/models` gains a `diar` list and `?kind=diar`. `settings.diarization.model` (default `community-1`) must exist in `[diar.*]` or startup fails. Tests use a fake registered under the id `pyannote` (`FAKE_DIAR_OVERRIDE=1`, plugin `fakes.diar`), the same trick as `FAKE_STT_OVERRIDE`; there is no `[diar.fake]` block.
5. **Settings section `[diarization]`** (all keys have defaults): `model`, `device` (`cpu|mps`), `merge_gap_ms = 1500`, `stall_s = 600`, `keepalive_s = 15`, `progress_min_interval_s = 1.0` (0 in tests), `plugins = ""` (test engines, like `[stt] plugins`). Env `DETAILS_DIARIZATION_<KEY>`.
6. **Token: env/.env only, and only for the download.** `settings.diarization.hf_token` is filled from `DETAILS_DIARIZATION_HF_TOKEN` or `HF_TOKEN` (env or `.env`); a `hf_token` key in `config.toml` is a startup error that says where to put it. The field has `repr=False` (tests look at `repr(settings.diarization)`; no code prints a settings object). `joblog.secrets_from` includes it and `redact()` also masks `hf_` + 20 or more alphanumerics. **`load_settings` merges `.env` into `os.environ`, so every child would inherit the token.** Therefore `settings.scrub_secret_env(env)` removes `HF_TOKEN`, `HUGGING_FACE_HUB_TOKEN` and `DETAILS_DIARIZATION_HF_TOKEN` from the server's own environment right after `__main__` loads settings (the value stays in `settings.diarization.hf_token`), protecting the STT worker, live worker, `lms` and the diarization worker alike. The diarization worker is additionally started through `env -u <3 names> HF_HUB_OFFLINE=1 HF_HUB_CACHE=<settings.paths.hf_hub>`, and sets the same itself (plus `PYANNOTE_METRICS_ENABLED=0`: pyannote 4.x otherwise reports usage to otel.pyannote.ai, found in task 9.1), so it works even if scrubbing is skipped. The token is never in `spec.json`, argv, API bodies, logs, `error` columns or exception text. `python -m details.diar_fetch` (`make diar-model`) is the only user: `snapshot_download(repo, cache_dir=settings.paths.hf_hub, token=...)`, errors passed through `redact()`.
7. **Availability (never crashes).** Two named seams in `services/models.py`: `pyannote_importable()` (guards `importlib.util.find_spec`, which RAISES `ModuleNotFoundError` for `pyannote.audio` when `pyannote` is absent, as it is in `.venv` today: checks `pyannote` first and catches `ModuleNotFoundError`/`ValueError`/`ImportError`, returns False) and `model_cached(hf_hub, repo)` (a snapshot directory with `config.yaml` AND at least one weight file `*.bin|*.safetensors|*.ckpt`; the weight-file rule is an assumption checked in task 9.2). No torch import. Reasons: not importable -> hint `make setup-diar`; no snapshot -> "speaker model is not downloaded", hint depends on token presence (no token: create a free Hugging Face token, accept the model terms, `HF_TOKEN=...` in `.env`, `make diar-model`; token: run `make diar-model` after accepting the terms); `config.yaml` without weights -> "download incomplete", rerun `make diar-model`. **A complete cached model with no token is available** (deviation from "token or model missing -> unavailable"; challenge it; flipping it is one condition). `POST` on an unavailable model answers 409 with reason + hint.
8. **Device: CPU default, MPS opt-in (`diarization.device`).** Evidence is thin on purpose: the community-1 model card (read through `design/v2/ml-engineer.md` section 3) documents CPU as the default and does not mention MPS; PyTorch documents that MPS does not implement every operator and offers `PYTORCH_ENABLE_MPS_FALLBACK=1` (docs.pytorch.org notes on MPS; not fetched in this session). So correctness on MPS is unproven and speed gain unmeasured. With `device=mps` the worker sets that fallback variable before importing torch. Task 12 (gpu) measures CPU vs MPS on one real clip and records both; the default flips only if the turns agree on at least 95% of frames (my threshold) and MPS is clearly faster.
9. **Audio input.** The adapter decodes with `ffmpeg` (`settings.record.ffmpeg` or PATH) to 16 kHz mono signed 16-bit PCM on a pipe and hands pyannote an in-memory `{"waveform", "sample_rate"}`. This avoids pyannote's own decoder (torchcodec/FFmpeg libraries), a known macOS install risk (unverified; task 9.1). Memory is O(duration): about 115 MB of int16 per hour plus a float32 copy (calculation, not measured).
10. **Heartbeat and stall guard.** Worker prints `alive` every `keepalive_s` starting at process start (model load can exceed the runner's 120 s heartbeat timeout), `loaded pyannote` after load, and `progress <phase> <done>/<total>` from pyannote's `hook` callback, at most one per `progress_min_interval_s` but never fewer than one per phase. The stall clock starts at process start and resets at load end and at every hook call; after `stall_s` without a reset the worker stops beating and the runner's heartbeat timeout kills it. The step turns `progress` lines into `ctx.progress` ("Speakers: embeddings 3/10"); the bar restarts per phase.
11. **Result file and ingest.** Worker writes `turns.json` (atomic) then `worker.done.json`. The step ingests in one transaction (idempotent: DELETE then INSERT): turns sorted, clipped to `[0, audio_ms]`, overlaps clamped, empties dropped; raw labels (`SPEAKER_00`) remapped to integers `1..n` by first appearance. `audio_ms` is `recording.duration_ms` read at step start (as `stt_transcribe` does). At step start the run is set `running` with `started_at` kept and `error` cleared (a job retry re-enters here after the finalizer wrote `failed`; the finalizer only touches `queued`/`running` rows). A missing run row is the plain error "diarization run not found". Plain worker errors: the worker writes `error.json` `{message}`; the step wraps `spawn_child`, on `StepError` reads `error.json` (redacted) and re-raises its message, else keeps the runner's. Zero turns = `done`, `speakers=[]`.
12. **Numbers are computed by code.** At completion the step stores `diarization_run.speakers` = `[{speaker, talk_ms, share_pct, turns}]`: `talk_ms` = sum of turn lengths, `share_pct` = share of total talk time (not of recording length) rounded to 1 decimal, so three equal speakers show 33.3 each and may sum to 99.9 (the UI shows whole percents), `turns` = count of same-speaker runs after merging gaps < `merge_gap_ms`. No LLM; no `speakers` output kind and no `output` row.
13. **Names are display-time and per diarization run.** `speaker_name` has primary key `(diarization_run_id, speaker)`. `PATCH /api/diarization-runs/{id}/speakers/{n}` `{name}` sets, `{name:null}` resets (PATCH, because `security.WRITE_METHODS` has no PUT, so a PUT would skip the cross-origin guard; a negative test sends a foreign `Origin`). The name is trimmed, NFC-normalised, 1-60 characters, no control characters, line breaks or `:` (it becomes `Name:` in prompts), unique per run after NFC + `casefold()` against the other speakers' display names and their default labels `Speaker N` (409), so "Speaker 2" cannot be given to speaker 1 even when speaker 2 has a name. Renaming never touches `transcript_segment`, `stt_run.text` or `diar_turn`.
14. **Alignment algorithm** (`services/diarization.py`, pure, unit-tested first): per segment, the speaker with the largest overlap in ms; ties go to the lower speaker number; no overlap -> `None` ("Unknown", never guessed). Words are not used (no engine gives word times today). `render_lines(segments, aligned, names, merge_gap_ms)` merges consecutive same-speaker segments with a gap below `merge_gap_ms` into `Name: text` lines (Unknown -> `Unknown:`).
15. **API.** `POST /api/recordings/{id}/diarization-runs {min_speakers?, max_speakers?, model_id?}` -> 202 `{diarization_run_id, job_id}`; `GET /api/recordings/{id}/diarization-runs` (each run with `job_id`, so a reload can resume watching); `GET /api/diarization-runs/{id}` (with `speakers` incl. display names); `GET /api/diarization-runs/{id}/turns`; `PATCH .../speakers/{n}`; `DELETE /api/diarization-runs/{id}` (409 while queued or running). `GET /api/stt-runs/{id}/segments?diarization_run_id=` adds `speaker` and `speaker_name`; without the parameter the response is what it is today (spec delta on `stt-runs`).
16. **Analyses use labels on request.** `POST /api/stt-runs/{id}/analyses` accepts optional `diarization_run_id` (must be `done`, same recording, and the STT run must have segments; else 422). It is stored on every `analysis_run` of the group (`api/analyses.py` insert; `steps_analyse.RUN_COLS` so retry rows copy it) and passed in the `analyse` step params, which is where the step reads it. The step builds `Name: text` lines (decision 14) with the names current at that moment and passes them as the existing `segments`. **Map-reduce:** the legend must not be lost in later chunks, so `generate_kind` gets `preface=""`, inserted at the start of the transcript text of every prompt (single pass and each chunk); the fixed sentence is "Each line starts with the speaker's name and a colon. Speaker labels are automatic and can be wrong. Never put a speaker name inside a quote." Prompt files are unchanged; the rendered prompt is already stored. `input_text_sha256` hashes what the model saw, so compare-runs will warn that a labelled and a plain analysis used different input. If the id in the params has no `done` run when the step starts (deleted), the step fails with a plain message; it never runs unlabelled.
17. **Terminal finalizer** `@steps.on_terminal("diarize")` sets `diarization_run` to `cancelled` / `failed` with the error text, including while still queued. No partial turns are kept on failure.
18. **Web.** New card "Who talked" on `/analyse` (`web/analyse/speakers.{js,css}`): optional min/max inputs, "Detect speakers" button (disabled with the API's reason and hint when unavailable; a line next to it says Live assist waits while speakers are detected), run picker, talk-time bars with colour **and** text `%` and `mm:ss`, a timeline of clickable blocks, a turns list `[mm:ss] Name text` (click or Enter seeks), rename inputs, the warning "Speaker labels are a guess. Check before sharing." and a second line that each transcript line gets one speaker so talk-time % and labelled text can differ. The transcript rows gain a speaker chip when a run is picked. The AI card gets a "Speaker labels" select. Progress reuses the Running card via `window.AnalyseJobs.watch(jobId, onFinish)` from `analyse.js`; on reload the card finds a queued/running run's `job_id` in the list and watches it. All text via `textContent`; no model id in page code.
18b. **GPU lease.** The `diarize` step runs under the existing `GpuLease` owner `job`, so a Live assist session requested meanwhile waits until the step ends (a running holder is never interrupted) and is then granted before other queued jobs. This is existing behaviour; this change adds a test that it holds for `diarize`, and the UI line above.
19. **Make targets and deps.** `requirements-diar.txt` (`pyannote.audio`; exact pins recorded after the first good install, task 9.1); `make setup-diar` installs it; `make diar-model` runs `details.diar_fetch`. `requirements.txt` is unchanged so default setup and tests do not need torch extras.
20. **Out of scope:** diagrams, live diarization, new STT models, merging two speakers, a cross-recording people table, voice identification, per-word speaker splitting, a `speakers` LLM output kind, using diarization to pick STT segments, German-specific tuning (diarization is acoustic).
